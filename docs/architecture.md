# Architecture

This document describes RealChat's architecture and technical boundaries. Sections marked **Planned** are not implemented yet. Product behavior is defined in [requirements.md](requirements.md), and decisions are recorded in [decisions.md](decisions.md).

## Current state

Implemented so far:

* **Configuration:** `backend/config/settings.py` loads and validates settings at startup. Errors name the problem setting but never its value.
* **Logging:** `backend/core/logging.py` writes JSON logs to stdout and redacts credentials, bot tokens, and sensitive fields.
* **Database:** `backend/database/engine.py` provides the async SQLAlchemy engine, the session factory, and a declarative `Base` with fixed constraint-naming rules. `migrations/` holds the Alembic migrations. The database URL comes from settings, never from `alembic.ini`. The schema is described in [database.md](database.md).
* **Users module:** `backend/modules/users/` holds the user, profile, terms-acceptance, and profile-change models (`models.py`), pure validation rules (`validation.py`), service functions (`service.py`) used by the bot's onboarding and profile management, terms text (`terms.py`), and country matching (`countries.py`). Database operations take a session and leave committing to the caller. Age and gender changes after onboarding go through `change_age` and `change_gender`, which lock the profile row, enforce the cooldown (D-019), and append to the change history (D-024).
* **Coins:** `backend/modules/coins/` holds the append-only coin ledger and coin holds (`models.py`) and the service for balances, credits, spending, and holds (`service.py`, D-050). Every change has an idempotency key; spending and holds lock the user's row while counting available coins. `backend/modules/coins/rewards.py` grants the welcome bonus and invite rewards when a profile is completed, grants the daily reward (`claim_daily`), and records invites from `/start inv_<code>` (handled in `apps/bot/onboarding.py`). `apps/bot/coins.py` handles 💰 /coins, which also shows the invite link and, while admins have it on, the daily reward with its 🎁 Claim button. Admin grants and corrections go through `apps/admin_cli.py` (`coins`, `balance`) and are audit-logged. Account deletion (`users.delete_account`) calls `coins.forfeit_all`, which releases held coins and removes the balance with one ledger entry (none for a zero balance), and `rewards.retire_invites`, which deletes the invite code and settles pending invites as not rewarded (D-055); a returning user's /coins lists only entries after `users.coin_history_after_id`, the account's last ledger entry at deletion. Credits lock the user's row like spending, so every ledger write is ordered with deletion.
* **Payments:** `backend/modules/payments/` sells coin packs and the VIP pass for Telegram Stars (D-061, D-062). `models.py` holds `stars_invoices` (what each invoice offered) and `stars_payments` (one row per Telegram charge); `service.py` lists the packs from admin settings, stores invoices, decides pre-checkout (`checkout_refusal`), and records a confirmed payment and credits its coins in one transaction (`fulfil`), with the buyer's row locked so it is ordered with account deletion. `apps/bot/payments.py` sends invoices from the /coins pack buttons, answers pre-checkout queries, handles payment confirmations (refunding a payment for a deleted account), and serves /terms and /paysupport. Its `RefundRetries` worker job retries refunds still owed, claiming a bounded batch whose retry time has come (`claim_refunds`, which skips rows another worker holds). VIP is `users.vip_until`: `is_vip` compares it with the current time, so expiry needs no job. `fulfil` grants a VIP pass in the same transaction: it takes the later of now and the current `vip_until`, adds the invoice's days, and stores the result as the new `vip_until`; it records the included coins as a `vip_coins` ledger entry, or no entry when the pass includes none; `can_buy_vip` limits buying to when at most one pass's length is left, checked when the button is pressed and again at checkout. `apps/bot/vip.py` serves /vip (status, the perks that work today, the pass, and its Buy or Extend button); /coins shows the status line too. A database trigger keeps payment rows from being deleted, freezes their charge, buyer, invoice, amount, creation time, and granted VIP end date, and a refund's note and shortfall once set, and lets the status only move forward. Refunds of fulfilled purchases (D-065): `refund_by_admin` (from the admin CLI) and `record_refund` (Telegram's `refunded_payment` report, handled by `on_refunded`) lock the payment row, take back its coins with one `purchase_refund` entry under `refund_key` and, for a VIP pass, rebuild `vip_until` from the user's other standing passes (`vip_end`), and move it to `refund_due` (the worker then sends it) or `refunded`; a shortfall and an admin's note are kept on the payment. The refund notice is sent, at most once, by whichever of the worker and `on_refunded` records the refund first. A confirmation that fails to be recorded is not resent by Telegram; `reconcile.py` compares stored payments with Telegram's transaction list for the admin CLI's read-only `reconcile` command, which pages through `getStarTransactions` (D-066). The CLI's `record-payment` replays such a payment through `fulfil` from Telegram's own record and sends the receipt, or the refund for a deleted account, with `apps/bot/payments.settle`, the same step the bot uses after a confirmation (D-068). `apps/bot/middlewares.is_payment` keeps payment updates, including refund reports, from being dropped by flood control or the restricted-account gate.
* **Admin module:** `backend/modules/admin/` holds runtime settings and the admin audit log (`models.py`), the list of settings with their defaults and allowed ranges plus a reader with a 10-second in-process cache (`settings.py`, D-035), and role, setting, and coin changes and purchase refunds (`service.py`). Every change is audit-logged. Roles (D-034) are changed only by the server-side CLI, `apps/admin_cli.py`, except that account deletion resets a role to `user`; a test checks that no bot module changes roles. The audit log is append-only in the database itself: triggers reject any update, deletion, or truncation. Because the application currently connects as the table owner, which could disable them, full protection needs a restricted application database role (O-011).
* **Redis:** `backend/core/redis.py` provides the client.
* **Bot:** `apps/bot/main.py` runs the aiogram dispatcher with long polling. Two Redis-backed outer middlewares (`apps/bot/middlewares.py`) run before every handler. The first claims each `update_id` before dispatch, with a short lease tagged by the running process. A duplicate that arrives while this process holds the lease is dropped. After the handler succeeds, the update is marked done and later redeliveries are dropped. If the handler raises, the claim is released. Note that aiogram confirms each update to Telegram once it has been received, whether or not the handler succeeded, so Telegram does not redeliver an update whose handler failed. That update is not retried, and the user receives the generic error and can try again. Telegram does redeliver updates that were never confirmed, which happens when the process stops or crashes mid-update. A lease left by a different process is therefore taken over immediately: Telegram allows only one long-polling consumer, so that process must have stopped, and its in-flight update is processed rather than lost. This rule must be revisited if webhooks with several workers are adopted (O-006). The second middleware drops updates from a user over a per-window limit. Both middlewares let updates through if Redis is unavailable, so side-effecting operations must carry their own database-level idempotency. `apps/bot/errors.py` logs handler failures with only the update id and type, the exception type, and the code location. It never logs the exception message, which could quote user input. The user receives a generic reply. `apps/bot/onboarding.py` handles `/start`, terms acceptance, and onboarding. The user's position is derived from the database where possible: terms acceptance (versioned, D-015) and the required fields (D-013). A user who leaves, or whose bot process restarts, therefore resumes at the right required step. Only the position within the optional steps (city, photo) and which text answer is expected are kept in aiogram FSM state in Redis. If that state is lost, a text message is not taken as an answer and the current step is asked again; a photo sent during the optional steps is still accepted. Because onboarding depends on that FSM state, it cannot proceed while Redis is unavailable, and the user receives the generic error. Each update gets its own database session (`apps/bot/db.py`). Handlers commit before sending replies, so no transaction stays open during a Telegram API call. Commands are never accepted as answers, and repeated or stale button presses are acknowledged without changing data. Onboarding runs only in private chats, so profile prompts and answers never appear in a group. Every handler that saves profile data first checks that the current terms version is accepted, and terms buttons carry the version they were shown with, so a button from older terms cannot accept newer ones. The dispatcher uses per-user event isolation, so a quick second message is not routed by state the first one is still changing. The locks are kept in Redis and expire after 60 seconds (D-018), so the process keeps no per-user lock memory, and isolation still holds if webhooks with several workers are adopted (O-006). `apps/bot/profile.py` handles `/profile`: it shows the user's profile card as others see it and lets each field be edited with the same validation as onboarding. It opens only after onboarding is complete and the current terms are accepted. Otherwise the user is taken to the terms or their onboarding step. Each edit gets a random id, kept in FSM state with the field being edited and carried by that prompt's buttons. A button from a cancelled, finished, or older edit therefore no longer matches and is answered as expired without changing anything. A profile without a photo is shown with a default avatar for its gender (`apps/bot/avatars.py`, D-020). Each image is uploaded once and then reused by its Telegram file identifier, cached in Redis per bot. The bot only ever stores Telegram file identifiers for user photos and never downloads image files. `apps/bot/account.py` handles Advanced settings, with the notification settings (D-052, stored in `notification_settings`; each button sets an explicit value, so a repeated or old tap never flips one back), 👻 Ghost mode for VIP users (D-064; set with a conditional update that requires VIP, so an old button after VIP ended changes nothing) and ◀️ Back to the profile card, and account deletion (D-025; confirmed by replying exactly DELETE, D-067, which the access gate lets through for restricted users, text or media but no command, only while their warning waits), and provides the access gate: an inner update middleware, registered after the database session, that stops suspended and banned users before any handler runs, except help, the terms, payment support, payment updates, and deletion (D-026, D-061). `apps/bot/admin.py` provides 🛠 Admin settings, offered inside Advanced settings to admins only. Every handler that shows or opens a setting re-checks the admin role and the current terms on the server, so an old or hand-made admin button from anyone else is answered as expired and changes nothing. Saving re-checks the role again inside the same transaction as the write, with the account row locked, so a role revoked meanwhile cannot slip through. Cancelling an edit and the "please send a number" reply change no settings and only affect the user's own pending edit. A saved change clears the bot process's settings cache at once; other processes see it within the cache time. `apps/bot/menu.py` handles `/help` (D-023) and defines the command menu, which the bot registers with Telegram for private chats at startup (D-022). Routers are tried in order (errors, menu, continue (✅ Continue, D-070), legal, payments, vip, account, coins, chat, safety, private, people, likes, direct, chat_requests, activity_alerts, relay, admin, profile, onboarding), so onboarding's final handler only sees messages no other handler took. Messages are sent with no parse mode, so user content can never be interpreted as markup; the welcome and the in-bot User Agreement and Privacy Policy are formatted with message entities instead (`apps/bot/legal.py`, D-070). Every request to Telegram passes through `apps/bot/telegram_session.py`: if Telegram rejects a button acknowledgement because the tap is too old or unknown, the rejection is ignored and the handler carries on with its action and reply. Any other Telegram error is raised as before. The test bot uses the same request middleware. The bot token is required by the bot, the worker, and the API, which checks the moderation Mini App's sign-in with it (`BotSettings`).
* **Moderation Mini App:** `apps/webapp` is a React, TypeScript, and Vite app (D-071), built into `apps/webapp/dist` and served by the API at `/moderation/` (`apps/api/moderation.py`); if it isn't built, that path is unavailable and the API still starts. Its API is under `/api/moderation/`. Every request carries Telegram's Mini App launch data in `Authorization: tma <launch data>`. The server checks Telegram's signature with the bot token (aiogram's `safe_parse_webapp_init_data`, the documented check), refuses data older than an hour or dated in the future, and re-reads the account's role and status on every request: only active moderators and admins get in (not suspended, banned, or deleted). There are no sessions or cookies, so nothing can be stolen from storage and there is no cross-site request forgery, and a removed role or a restriction takes effect on the next request. A 401 means the launch data is missing, forged, or too old; a 403 means the account may not use the panel; neither says which check failed. Panel and API responses carry a strict content security policy (the panel's own files and Telegram's official script only, framing only by Telegram Web), `no-store`, `nosniff`, and `no-referrer`. Reviewing reports (`backend/modules/moderation/review.py`): `GET /api/moderation/reports` lists open reports, urgent first, without content. `GET /api/moderation/reports/{id}` returns one report with the reporter's and the reported person's cards, the reported person's record (warnings, suspensions, bans, and reports received), and the content. A chat report shows its conversation's stored messages from both people; a profile report shows the direct messages and chat requests between the two. Each opening is audited (`report_viewed`). Telegram ids and file references are never returned. `POST .../media` sends one item to the moderator's own Telegram chat by its file reference, protected from forwarding and saving, only if it belongs to the report (a message in that conversation, a direct message between those two, or the reported profile's photo). The copy is queued in `telegram_deletions` for deletion 10 minutes later (the worker deletes it then, or as soon as it can), and the view is audited (`media_viewed`). The API holds its own bot client for this and commits before calling Telegram; if the view can't be recorded afterwards, it tries to delete the copy at once; if Telegram refuses or can't be reached, the copy can stay, and the failure is logged. A review shows up to the latest 2,000 messages. `POST .../action` closes, warns, suspends, or bans through `actions.act` with the report, so every rule of D-071 applies; a refusal is a 409 with its reason. Account lookup (`backend/modules/moderation/lookup.py`): `GET /api/moderation/accounts?query=` finds the account with a RealChat ID, as typed or as the bot shows it (`/userid_<id>`): only accounts that aren't deleted and finished onboarding, restricted ones included. Audited (`account_looked_up`). Every account endpoint checks the same rule (`lookup.findable`), so a known or guessed internal id can't reach an account a search wouldn't find, such as one deleted since; opening an account is audited (`account_viewed`). `GET .../accounts/{id}` returns the card, status, suspension end, record, and the reports received and made, which open in the report review. `POST .../accounts/{id}/action` warns, suspends, bans, or lifts through `actions.act` with no report. Admins only, each with a reason of 5 to 300 characters saved in the audit log's `reason` column: `POST .../threads` lists the account's stored conversations and direct-message threads without content (`chats_listed`), `POST .../threads/open` returns one (`chat_opened`), refused unless the account took part in it, and `POST .../media` sends a media item from one of its threads like report media. The screens (`apps/webapp/src`) switch between the queue and a report with Telegram's back button, and confirm every action in Telegram's own popup before sending it. Component tests (Vitest, React Testing Library, jsdom) run in CI. The bot shows 🛡 Moderation (an inline Mini App button) in Advanced settings to moderators and admins only, once `PUBLIC_BASE_URL` is set. The app's npm packages are pinned exactly in `package-lock.json`, installed with `npm ci` and no install scripts, and audited in CI.
* **API:** `apps/api/main.py` serves `/terms` (the User Agreement) and `/privacy` (the Privacy Policy) (`apps/api/pages.py`, D-069, D-070: self-contained HTML with their headings, from the same source as the bot's, with a strict content security policy), `/health` (the process is running), and `/ready` (PostgreSQL and Redis are reachable, each checked with a 2-second timeout). Failure details go to the server log and never into the HTTP response. Interactive docs and the OpenAPI schema are disabled.
* **Local services:** `docker-compose.yml` runs PostgreSQL 18 and Redis 8, both ARM64-compatible, bound to `127.0.0.1` only.

* **Matching and chat:** `backend/modules/matching/queue.py` keeps searches in Redis: a sorted set of searching users plus one key per user holding the state of their current search (searching, held by the matcher, or cancelled while held) (D-027). Every change that touches both is atomic, run as a single Lua script. A search cancelled while the matcher holds it is never put back, and a queue entry whose search key has expired is discarded rather than matched. A claim marker expires after 60 seconds, so one left behind by a failed release cannot block new searches for long; a failed release after a committed match is logged and the match is still announced. `backend/modules/matching/matcher.py` pairs searchers (D-041); `backend/modules/chat/` holds the conversation tables and the service that starts, finds, and ends conversations, checks eligibility, and finds recent partners. `apps/bot/chat.py` handles 🎭 New Anonymous Chat, which opens the "Who do you want to meet?" menu (D-044); the menu's random-chat button starts a search, with a Cancel button bound to that search. It also handles 👤 Partner profile and ⏹ End chat, and provides `ChatNotifier`, which the worker uses to announce matches, ended searches, and idle-chat warnings and endings. `apps/bot/endings.py` holds the menu and the messages for each way a chat can end. Every ending tells each user how it ended, restores the main keyboard, offers Block (or Unblock) and Report for that chat, and shows the menu again. `apps/bot/keyboards.py` defines the main and chat keyboards; the bot shows the chat keyboard while the user is in a chat. `apps/bot/relay.py` relays supported messages from a user in a chat (D-028, D-036, D-038, D-042, D-043):
  1. The sender must have accepted the current terms; otherwise the terms are shown and nothing is stored or relayed. The message is then checked against the sender's open conversation in PostgreSQL. It is also checked against `backend/modules/chat/content.py` and the bot's own checks: no contact cards, locations, links, phone numbers, or @usernames, including links and mentions hidden in formatting, link buttons, and look-alike or invisible characters.
  2. It is recorded in `chat_messages` and the transaction is committed, so a redelivery is never relayed twice.
  3. It is copied to the partner with `copyMessage` and `protect_content`. No sender is shown, and Telegram apps that honour protection block forwarding and saving.
  4. The record is linked to the copy in a transaction that share-locks the conversation. If the chat ended meanwhile, or linking fails, the copy is deleted again. This is best effort: if Telegram refuses the deletion, it is logged and the copy remains.

  Content Telegram cannot copy gets a short notice and the chat continues. When the replied-to message can be identified, a reply is pointed at the matching message on the partner's side; otherwise it is sent as a plain message. Edits to text and captions are mirrored, under the same content checks and terms requirement, and only while no other step is waiting for an answer. A redelivered message is relayed once. If the partner blocked the bot or is gone, the chat ends as `unreachable` and the sender is told. The relay passes over users who are not in a chat, commands, and messages while another step (such as a profile edit) is waiting for an answer, so those reach their usual handlers. Message content never appears in ordinary logs. An album is relayed as separate messages, because each item reaches the bot as its own message.
* **Blocking and reporting:** `backend/modules/moderation/` holds the `user_blocks` and `reports` tables and the service that blocks, unblocks, and files reports (D-037, D-045, D-054). A chat action names a conversation, and the service acts only on the other participant of a conversation the user was in. Blocking or reporting ends that conversation if it is still open, through the chat service, which never ends a different, newer conversation. A profile action names a user instead and stores no conversation: it needs a profile visit between the two, either way round, within the visits window, checked after the account rows are locked so a concurrent deletion can't be missed, and it ends no chat. A profile button pressed after the two have chatted acts on their latest chat instead. `apps/bot/safety.py` handles the Block, Unblock, and Report buttons and the optional report details. Blocks do not affect matching. `backend/modules/moderation/actions.py` holds the moderation actions (D-071): closing a report with no action, warning, suspending for a fixed number of days, banning, and lifting a suspension or ban. `act` locks the actor's and the target's account rows in id order, then the report, which must still be open, so a report is closed by exactly one action and the actor's role is checked as it stands. Moderators cannot lift bans, act on staff, or act on themselves. In the same transaction, suspending or banning ends the account's open chat (end reason `restricted`), the action is recorded in `moderation_actions` and the audit log, and what it owes people goes into `moderation_notices`. That covers the action notice, the reporter's notice (whether action followed, never which), and the chat partner's notice. Searches by restricted accounts are dropped by the matcher as before. `users.suspended_until` holds a suspension's end; `moderation_actions.standing` lifts an ended suspension when the user's next update reaches the access gate.
* **People:** `backend/modules/people/service.py` lists a user's past chat partners and checks that a past chat can be opened (D-051): a conversation the user was in, ended within the window (an admin setting), after both users' latest account deletion, with a partner whose account is active and onboarded, and no open chat between them. `apps/bot/people.py` handles 👥 People on the profile card, the 💬 Past chats pages, and opening a partner's card; every button is checked again on the server, so an old or forged one opens nobody. `backend/modules/people/visits.py` records profile visits (none while the visitor is VIP with Ghost mode on, `users.ghost_mode`, D-064), decides whether a visit is announced, lists Visited you, and holds `VisitRetention`, the worker's daily job that deletes expired visits (D-053). `apps/bot/people.py` also handles 👀 Visited you, visitors' cards, and the visit notices, sent after the transaction commits and best effort; `apps/bot/chat.py` records a visit when 👤 Partner profile is opened. `apps/bot/cards.py` holds the profile caption and `send_card` (the photo or default avatar with the caption), which /profile, the chat partner card, People, and /userid all use, each with its own buttons. Each caller passes whether the profile's owner is VIP now, and `apps/bot/badges.py` adds the VIP badge to card and list names and the ✅ to names in notices (D-063). Every caption shows the profile's RealChat ID (`profiles.public_id`, drawn by `backend/modules/users/public_ids.py`) as `/userid_<id>` (D-054). `apps/bot/people.py` also handles `/userid`: it looks the ID up with `users.find_profile`, which returns only active, onboarded accounts, so every other case gets the same "No profile with that ID". Wrong lookups are counted in Redis (`backend/modules/people/lookups.py`, one key per user that expires an hour after the first miss); at the admin limit every lookup is refused until it expires, and lookups are refused if Redis is unavailable. Another user's card opened by ID or from Visited you has Block and Report for the latest chat the two shared, or, if none, profile Block and Report (`ProfileSafetyAction` in `apps/bot/endings.py`, handled in `apps/bot/safety.py`). Those carry the RealChat ID, and `moderation.check_met` requires a profile visit between the two, either way round, before a profile block or report. `backend/modules/people/likes.py` records likes and lists Liked you and You liked (D-056); a like locks both account rows like a visit, upserts the pair's single row, and claims the notice with a conditional update of `notified_at`, so concurrent taps add one like and send at most one notice within the admin-set gap. `apps/bot/likes.py` handles ❤️ Like and 💔 Unlike (`LikeAction` in `apps/bot/endings.py`, carrying the RealChat ID, checked again on every tap) and sends the like notice after the transaction commits, best effort. Every other user's card puts the like row above Block and Report, and the safety buttons keep it when they change. `apps/bot/people.py` handles the two like lists and their cards. `apps/bot/db.py` also records RealChat activity (`users.last_active_at`) in a middleware registered after the access gate, writing at most once a minute per user and committing before the handler runs.
* **Private mode:** `backend/modules/chat/private.py` turns Private mode on and off, links relayed messages to the active session, ends sessions, and keeps the queue of Telegram messages to delete (D-031, D-047). `apps/bot/private.py` handles the 🔒/🔓 buttons, tells both users, and provides the worker's notifier and `TelegramDeletions`, which deletes queued messages in batches. It also handles view-once media (D-048): the relay sends Private mode photos, videos, voice messages, and video messages as a tap-to-view placeholder, and the 👁 View button opens one once. The opened copy, the placeholder, and the sender's original are deleted after the stored viewing time (the view timer plus the length of a video, voice message, or video message), as far as Telegram's 48-hour limit on deleting messages allows. Media sent within a short window (admin setting, default 30 seconds; 0 turns it off) after the partner turned Private mode off, or after it reached its time limit, is held by the relay: the sender chooses Send or Don't send, and an unanswered question lapses after 10 minutes (D-049).
* **Direct messages:** `backend/modules/direct_messages/` holds the `direct_messages` table and the service (D-057). Sending locks both account rows, checks eligibility and blocks both ways, holds the price (`coins.hold`, purpose `direct_message`), and records the message as pending under a key naming the Send; the caller commits, sends the recipient's notice, and then settles it: `delivered` captures the hold, `failed` releases it and records why. Opening and the free reply check the recipient, the status, and the retention period on the server. `apps/bot/direct.py` handles ✉️ Message (`DirectAction` in `apps/bot/endings.py`, carrying the RealChat ID), the message prompt and preview (aiogram FSM state, so the relay skips those messages), Send, Open, and ↩️ Reply (free). It checks content with the relay's rules (`content_refusal`) and shows stored content with `send_content`, protected. People cards (`apps/bot/people.py`) put the Message row under Like, except for the current chat partner or when the card's owner blocked the viewer; the safety buttons keep both rows when they change.
* **Chat requests:** `backend/modules/chat_requests/` holds the `chat_requests` table and the service (D-058). Sending checks both users (activity within the admin window from `users.last_active_at`, open chats, Silent mode, blocks both ways, one waiting request per pair), holds the price, and records the request as pending; the bot sends the notice and settles it as for direct messages. `connect` share-locks both accounts, locks the request, ends any open chat either is in, and starts their conversation, all in one transaction; on a unique-index conflict (one of them was matched meanwhile) the caller rolls back. `apps/bot/chat_requests.py` handles 💬 Chat request (`RequestAction` in `apps/bot/endings.py`), the confirmation, Send, Accept (with the busy recipient's confirmation), Decline, and the busy sender's Switch or Stay. After connecting it ends both users' searches through the queue (returning a paid search's hold) and announces the chat to both. People cards add the Chat request row under Message, with the same visibility.
* **Activity alerts:** `backend/modules/activity_alerts/` holds the `activity_alerts` table and the service (D-059). Buying checks both users, blocks, the person's opt-out (`notification_settings.activity_alerts`), and one active alert per pair, then writes the alert and its `activity_alert` ledger entry together. Firing compares the person's `users.last_active_at` (RealChat activity, D-051) with the purchase time; refunds credit `activity_alert_refund` under a key. `apps/bot/activity_alerts.py` handles 🔔 Alert when active (`AlertAction` in `apps/bot/endings.py`), the confirmation, Buy, and Cancel. People cards add the row under Chat request, showing Cancel while an alert is set.
* **Worker:** `apps/worker/main.py` runs the matcher and the idle-chat job (`backend/modules/chat/idle.py`, D-039) about once a second in one loop; both tell users by Telegram (match announcements, idle warnings and endings) from that loop. Eleven other jobs each have a loop of their own, so they never hold up matching: the Private mode job (ending sessions whose chat ended or that reached the time limit, and telling both users) and Private mode deletions, each about once a second; the chat retention job (`backend/modules/chat/retention.py`, D-046), which normally does its work once a day (retrying within the hour after a failure or crash) and deletes stored chat messages past the retention period except those under an open report; and the profile visit retention job (`backend/modules/people/visits.py`, D-053), which runs the same way and deletes visits past their retention period. The chat retention job also deletes direct messages past the same period, and a sweep (`PendingSweep` in `backend/modules/direct_messages/service.py`, about once a minute) fails direct messages left pending by an interrupted Send and releases their held coins (D-057). The chat request job (`RequestJobs` in `backend/modules/chat_requests/service.py`, every few seconds) fails interrupted requests, expires unanswered ones, and lapses busy senders' switches, then tells the users through `RequestNotices` (D-058). The activity alert job (`AlertJobs` in `backend/modules/activity_alerts/service.py`, every few seconds) fires and refunds alerts and tells the buyers through `AlertNotices` (D-059). The moderation job (`ModerationNotices` in `apps/bot/moderation.py`, every few seconds, D-071) lifts suspensions that have ended, then claims due notices with `FOR UPDATE SKIP LOCKED`, moving each one's next attempt ahead, and marks them sent once Telegram accepts them or never can (the person blocked the bot); other failures are retried a few times. The staff alerts job (`StaffAlerts` in `apps/bot/moderation.py`, every few seconds, D-071) writes the day's summary of open reports once its hour has passed (an admin setting, India time) and sends due alerts in `staff_alerts`: urgent reports, written when filed, and the summary, with an Open button into the Mini App once `PUBLIC_BASE_URL` is set (`?report=<id>` opens that report). The daily reward reminder job (`ReminderJob` in `backend/modules/reminders/service.py`, about once a minute) records each due reminder before sending it through `ReminderMessages` (`apps/bot/reminders.py`), in paced batches (D-060); a user's time follows their latest claim, else their country's local hour (`backend/modules/reminders/timezones.py`, from `tzdata`). The idle job ends chats that were warned at least the grace time ago with no message since, then warns chats with no relayed message for the idle-notice time. Both times are admin settings. It commits before telling anyone, and locks each chat row while skipping rows that are locked, so a message being recorded is never cut off and each chat is warned and ended once.

  The matcher: each tick takes a Redis lock (30 seconds, not renewed), so normally only one matcher runs even with several workers. Correctness does not depend on the lock: a pair is claimed from Redis atomically, and the database refuses a second open conversation, so an overlapping tick cannot create a double match. It ends searches past the time limit (an admin setting) and tells those users; re-checks waiting users in PostgreSQL (active account, onboarding complete, current terms, no open conversation) and drops anyone ineligible; pairs the rest oldest first, avoiding partners from the last few minutes while anyone else is waiting (D-033), and swapping partners between pairs where that avoids a repeat; each tick considers at most the 200 longest-waiting searches still within the time limit, so an alternative further back in a longer queue is not seen in that tick, plus every VIP search, which a VIP's search start also records in a second sorted set (`match:vip`, D-063); VIPs confirmed in PostgreSQL are paired first, oldest first; then, for each pair, takes both out of the queue atomically, re-checks them with their user rows share-locked and creates the conversation in one transaction, and only after that commit tells both users. Account deletion locks the same row first, so a deletion and a match never interleave. If the database refuses the match, whoever is still eligible goes back to their old place in the queue; on any database error both go back before the error is raised. A failed tick is logged without exception messages and the next one runs as usual.

  Paid searches (D-050): a search's id in Redis carries the gender it is for (`<token>-<gender>`), and its coins are held in PostgreSQL (`coin_holds`) under the idempotency key `search:<user id>:<token>`; no coin state is kept in Redis. The matcher pairs two searchers only if each one's gender fits the other's choice (a free search fits anyone), never swaps into a pair that doesn't fit, re-checks both users' choices (from the searches it claimed) and genders (share-locking the profiles) and captures the paid users' holds in the same transaction that creates the match (no match if they no longer fit or a hold can't be captured), and releases a hold when its search ends without a match. Stale paid-search holds are released each tick as a safety net.

The moderation Mini App exists (see above); the user-facing Mini App does not exist yet.

## Overview (planned)

RealChat is a **modular monolith**: one codebase with shared business modules, run as several processes. There are no microservices and no Kubernetes.

```
 Telegram users
      │
      ▼
 Telegram Bot API ◄────────────► Bot process (aiogram)
                                   │
 Mini App (React, in Telegram) ──► API process (FastAPI)
                                   │
                                   ▼
                   Shared backend modules (business rules)
                                   │
                ┌──────────────────┼──────────────────┐
                ▼                  ▼                  ▼
          PostgreSQL            Redis           Worker process
        (source of truth)  (queues, caches,    (expiry, refunds,
                            rate limits)        notifications,
                                                cleanup)
```

### Processes

| Process | Responsibility |
|---|---|
| Bot | Receives Telegram updates. Handles commands, onboarding conversations, callbacks, and message relay between matched users. |
| API | Authenticated endpoints for the Mini App and admin tools, health checks, and Telegram webhooks if those are chosen (decision O-006). |
| Worker | Scheduled and background jobs: chat-request expiry, refunds, notifications, and retention cleanup. Payment reconciliation is an admin CLI command, run by hand (D-066). |
| Mini App | Optional React and TypeScript interface opened inside Telegram. It is never required for onboarding, matching, or chatting. |

All processes call the same backend modules. Bot handlers, API routes, and frontend components contain no business rules of their own.

### Data stores

* **PostgreSQL** is the source of truth for users, profiles, conversations, the coin ledger, payments, subscriptions, reports, and audit records.
* **Redis** holds temporary state only: matching queues, rate-limit counters, caches, and short-lived locks. If Redis loses data, no payment, balance, or account record can be lost or duplicated.

### Planned repository layout

The layout follows requirements §24. Folders are added only when they are needed.

```
apps/        entry points: bot, api, worker, miniapp
backend/     shared code: config, database, integrations, and domain modules
migrations/  Alembic migrations
tests/       unit, integration, security, concurrency, end-to-end
infra/       Docker, reverse proxy, server scripts
docs/        requirements, architecture, decisions, and later security and deployment docs
```

## Key invariants (planned)

* Every coin balance change is an immutable ledger entry written inside a database transaction with a unique idempotency key.
* A match, charge, refund, or payment fulfilment happens at most once, even when a Telegram update is retried or delivered twice.
* No message is relayed unless the sender and recipient are both participants in the same active conversation.
* Exact coordinates are never shown to other users.

## Target infrastructure (planned)

* A single Oracle Cloud Always Free ARM64 (Ampere A1) server, if one is available to the account, running every process plus PostgreSQL and Redis under Docker Compose.
* Caddy or Nginx in front, providing HTTPS.
* PostgreSQL and Redis are never exposed to the internet.

A single server provides no high availability. See `docs/deployment.md`, once it is written.
